# 확인 질문

## 제품 방향

1. 현재 결정: 내부 운영 도구나 전문 SaaS가 아니라, 소수의 외부 사용자를 대상으로 하는 개인용 성격의 서비스로 정의한다.
2. 구독자는 우선 사람 중심으로 본다. 자동화 시스템 연동은 후순위로 둔다.
3. 현재 결정: 상태를 보는 것이 핵심이며, 에이전트 제어는 초기 범위에서 제외한다.

## 에이전트 환경

1. 에이전트들은 어떤 언어와 런타임으로 만들어져 있나요?
2. 에이전트가 항상 네트워크에 연결되어 있나요, 아니면 오프라인/간헐 연결 환경도 있나요?
3. 현재 결정: Agent의 hook, skill, 실행 결과에 의존한다.
4. hook으로 지침 원문, 체크박스, 테스트 결과까지 안정적으로 전달할 수 있나요?

## 상태와 진행률

1. 현재 결정: 지침마다 다르므로 가변 단계 모델을 사용한다.
2. 지시 하나가 여러 에이전트에 나뉘어 수행될 수 있나요?
3. 에이전트가 동시에 여러 지시를 처리할 수 있나요?
4. 사용자 입력 대기 상태를 시스템이 다뤄야 하나요?
5. 지침 안의 체크박스 형식은 Markdown 체크박스를 기준으로 보면 되나요?
6. 테스트 완료 상태는 에이전트가 명시적으로 보내나요, 아니면 산출물이나 로그에서 추론해야 하나요?

## 실시간성

1. 상태 변화는 몇 초 이내로 전달되어야 하나요?
2. 구독자가 접속하지 않았던 동안의 이벤트를 나중에 다시 받아야 하나요?
3. 현재 결정: 대시보드 갱신과 알림이 우선이며, 외부 Webhook은 후순위로 둔다.
4. 브라우저 알림은 모든 완료 이벤트에 보낼까요, 실패/테스트완료 같은 중요 이벤트에만 보낼까요?

## 저장과 보안

1. 이벤트 이력을 얼마나 오래 보존해야 하나요?
2. 이벤트 payload에 민감한 데이터, 개인정보, API 키, 내부 문서 내용이 포함될 수 있나요?
3. 프로젝트별 접근 권한을 엄격히 분리해야 하나요?

## 운영

1. 예상 에이전트 수와 초당 이벤트 수는 어느 정도인가요?
2. 현재 결정: 브라우저 알림과 페이지 내부 모달 알림을 우선한다.
3. 기존에 사용하는 모니터링, 로그, 알림 시스템이 있나요?

## 초기 구현 범위 제안

현재 정보만 기준으로는 다음 범위를 1차 MVP로 제안합니다.

- 에이전트가 hook 또는 skill 결과로 HTTP API에 상태 이벤트를 전송한다.
- 서버는 PostgreSQL에 이벤트와 최신 상태를 저장한다.
- 서버는 지침별 가변 단계, 체크박스, 테스트 완료 상태를 정제해 저장한다.
- 대시보드는 프로젝트별 에이전트와 지침 상태를 보여준다.
- 실시간 갱신은 Server-Sent Events로 시작한다.
- 브라우저 알림과 페이지 내부 모달 알림을 제공한다.
- RabbitMQ는 알림 재시도와 내부 비동기 처리가 필요해지는 시점에 도입한다.
