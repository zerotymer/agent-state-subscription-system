# 요구사항 초안

## 목표 사용자

- 외부 사용자: 소수의 사용자가 자신이 관심 있는 프로젝트와 지침의 진행 상태를 확인한다.
- 프로젝트 소유자: 여러 프로젝트의 에이전트 실행 상태와 완료 여부를 한눈에 확인한다.
- 개발자: 에이전트가 어떤 지침을 수행 중인지, 어디서 실패했는지 추적한다.
- 자동화 시스템: 특정 상태 변화에 반응해 후속 알림 또는 저장 작업을 실행한다.

## 주요 개념

### Project

에이전트가 소속되거나 작업이 발생하는 논리 단위이다.

예:

- 문서 자동화 프로젝트
- 크롤링 네트워크 프로젝트
- 코드 리뷰 자동화 프로젝트

### Agent

작업 지시를 수행하는 실행 주체이다. 한 프로젝트에 여러 에이전트가 있을 수 있고, 하나의 에이전트가 여러 프로젝트에서 사용될 수도 있다.

### Instruction

에이전트에게 전달된 작업 지시 또는 명령이다.

예:

- 특정 문서 요약
- 저장소 검사
- 배치 데이터 수집
- 보고서 생성

### State Event

에이전트 또는 지시의 상태 변화를 나타내는 이벤트이다.

예:

- `registered`
- `assigned`
- `queued`
- `running`
- `progressed`
- `waiting_input`
- `blocked`
- `completed`
- `failed`
- `cancelled`
- `retrying`

### Subscription

특정 조건에 맞는 상태 이벤트를 받아보는 개념이다. 단, 이 프로젝트에서의 구독은 일반 pub/sub보다 `agent -> hook -> web layer` 단방향 수신에 가깝다.

예:

- 특정 프로젝트의 모든 에이전트 상태
- 특정 지시의 진행률
- 특정 지침의 체크박스 완료 상태
- 테스트까지 끝난 최종 완료 이벤트
- 실패 또는 차단 이벤트

## 기능 요구사항

### 에이전트 등록

- 에이전트는 고유 ID, 이름, 유형, 소속 프로젝트, 기능 태그를 가진다.
- 에이전트의 현재 실행 환경, 버전, 상태 수신 방식도 기록할 수 있어야 한다.
- 에이전트가 일시적으로 오프라인인지, 폐기되었는지 구분할 수 있어야 한다.

### Hook 기반 상태 수신

- 에이전트는 hook, skill, 실행 결과, 상태 이벤트 중 가능한 방식으로 진행 정보를 전송한다.
- 웹 계층은 받은 정보를 정제하여 저장 가능한 상태 모델로 변환한다.
- 이벤트에는 최소한 다음 정보가 포함되어야 한다.
  - 이벤트 ID
  - 발생 시각
  - 프로젝트 ID
  - 에이전트 ID
  - 지시 ID
  - 상태 코드
  - 진행 정보 또는 단계 정보
  - 지침 내용 또는 지침 요약
  - 체크박스 상태
  - 테스트 수행 여부와 테스트 결과
  - 메시지
  - 원인 또는 오류 정보
  - 관련 산출물 참조
- 이벤트는 중복 수신될 수 있으므로 멱등 처리가 필요하다.

### 진행 정도 표현

- 진행률은 0-100 숫자만으로 제한하지 않는다.
- 다음 표현을 함께 지원한다.
  - 단계명
  - 현재 단계 번호와 전체 단계 수
  - 체크리스트
  - 로그 요약
  - 예상 완료 시각
  - 사용자의 입력 대기 여부
- 지침별 단계 수와 체크박스 수는 가변으로 처리한다.
- 최종 상태는 단순 `completed`보다 `completed_and_tested`처럼 테스트 완료 여부를 분리해서 확인할 수 있어야 한다.

### 구독

- 구독자는 프로젝트, 에이전트, 지침, 상태 코드, 체크박스, 테스트 완료 여부 조건으로 상태를 필터링할 수 있어야 한다.
- 에이전트에서 웹 계층으로의 기본 수신 방식은 hook 기반 단방향 전송으로 본다.
- MCP를 사용하는 경우에도 직접 명령 실행이 아니라 Agent가 주기적으로 읽는 상태 기반 간접 지시를 사용한다.
- 웹 계층에서 사용자에게 뿌려주는 방식은 페이지 갱신, 브라우저 알림, 페이지 내부 모달 알림으로 구분한다.
- RabbitMQ 또는 MQTT는 초기 필수 조건이 아니라 내부 분배와 알림 안정화 수단으로 검토한다.
- 나중에 접속한 사용자는 최신 상태 스냅샷과 지침별 진행 타임라인을 조회할 수 있어야 한다.

### Agent 연결성

- Agent는 주기적으로 heartbeat를 보내거나 MCP 상태를 갱신해야 한다.
- Agent는 지침을 읽었는지 여부를 `acknowledged`로 표시할 수 있어야 한다.
- 웹 계층은 desired state와 actual state를 분리해 저장해야 한다.
- Agent가 일정 시간 응답하지 않으면 `offline` 또는 `stale`로 표시해야 한다.
- SSH와 같은 강제 원격 제어 방식은 사용하지 않는다.

### 신뢰도 계층

- 최초 지시문, 전체 방향성, 테스트 요구사항, 취소/재시도 요청은 높은 신뢰도 영역으로 처리한다.
- 높은 신뢰도 영역은 MCP 기반 상태 조회, acknowledge, 지침 버전 관리를 우선 적용한다.
- 기본 진행 단계, 최근 수행 작업, 직전 지시, heartbeat, lifecycle report는 중간 신뢰도 영역으로 처리한다.
- 중간 신뢰도 영역은 hook, snapshot, heartbeat로 정기 보고한다.
- 모든 이벤트에는 필요 시 `reliability_level`을 기록할 수 있어야 한다.

### 상태 조회

- 프로젝트별 현재 상태 목록을 조회할 수 있어야 한다.
- 지시별 타임라인을 조회할 수 있어야 한다.
- 에이전트별 최근 이벤트와 실패 이력을 조회할 수 있어야 한다.
- 장애가 반복되는 에이전트나 지시를 탐지할 수 있어야 한다.

### 알림

- 실패, 지연, 사용자 입력 대기, 완료, 테스트 완료 이벤트에 대해 알림을 보낼 수 있어야 한다.
- 알림 채널 후보:
  - 브라우저 알림
  - 페이지 내부 모달 알림
  - 대시보드 상태 표시
  - Webhook
  - 이메일 또는 메신저

## 비기능 요구사항

### 신뢰성

- 핵심 상태 이벤트는 유실되지 않아야 한다.
- 일시적 네트워크 장애가 있어도 재전송 또는 재처리가 가능해야 한다.
- 이벤트 순서가 뒤섞일 수 있으므로 발생 시각과 버전을 기준으로 정렬할 수 있어야 한다.

### 확장성

- 프로젝트와 에이전트 수가 증가해도 구독 필터링과 조회 성능이 유지되어야 한다.
- 상태 이벤트 저장소와 실시간 전달 계층은 분리 가능해야 한다.

### 보안

- 프로젝트별 접근 권한을 분리해야 한다.
- 에이전트와 서버 간 통신은 인증되어야 한다.
- 이벤트 메시지에 민감한 데이터가 포함될 수 있으므로 저장 정책과 마스킹 정책이 필요하다.
- 외부 공개 endpoint는 Next.js BFF 계층으로 제한한다.
- 사람 사용자는 SSO와 session cookie로 인증한다.
- Agent와 MCP/API client는 API Key로 인증한다.
- Agent 인증에 아이디/비밀번호를 사용하지 않는다.
- API Key 사용량과 마지막 사용 시각을 조회할 수 있어야 한다.

### 관측성

- 수집 서버 자체의 상태도 모니터링해야 한다.
- 이벤트 지연, 실패율, 재시도 횟수, 구독자 연결 수를 지표로 남겨야 한다.
