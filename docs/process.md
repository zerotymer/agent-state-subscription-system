# 프로세스 초안

## 1. 프로젝트 등록

1. 운영자가 프로젝트를 등록한다.
2. 프로젝트 ID와 접근 권한이 생성된다.
3. 상태 수집 정책과 보존 기간을 설정한다.

## 2. 에이전트 등록

1. 에이전트가 API 또는 관리 화면을 통해 등록된다.
2. 에이전트 유형, 기능, 버전, 소속 프로젝트를 기록한다.
3. 에이전트 인증 토큰 또는 클라이언트 자격 증명을 발급한다.
4. 에이전트는 주기적으로 heartbeat 이벤트를 발행한다.

## 3. 지침 공유 또는 생성

1. 사용자 또는 시스템이 에이전트에게 지침을 전달한다.
2. 가능하면 지침 원문 또는 요약을 웹 계층에도 공유한다.
3. 지침에 Markdown 체크박스나 단계 목록이 있다면 별도 진행 항목으로 추출한다.
4. 지침은 프로젝트와 에이전트에 연결된다.
5. 초기 상태는 `queued` 또는 `assigned`로 기록한다.
6. 사용자는 새 지침 상태를 대시보드에서 확인한다.

## 4. Hook 기반 상태 수신

1. 에이전트는 작업 시작 시 hook으로 `running` 상태를 보낸다.
2. 단계가 바뀌거나 체크박스가 완료될 때 `progressed` 상태를 보낸다.
3. 사용자 입력이 필요하면 `waiting_input` 상태를 보낸다.
4. 외부 의존성 문제나 반복 실패가 있으면 `blocked` 상태를 보낸다.
5. 작업 구현이 끝나면 `completed` 상태를 보낸다.
6. 테스트 또는 검증까지 끝나면 `tested` 또는 `completed_and_tested` 상태를 보낸다.
7. 실패 시 `failed`, 취소 시 `cancelled` 상태를 보낸다.

## 5. MCP 기반 간접 지시

MCP를 사용하는 경우에도 웹 계층은 Agent를 직접 강제 제어하지 않는다.

1. 웹 계층은 지침의 desired state를 저장한다.
2. Agent는 정해진 주기에 MCP를 통해 desired state를 읽는다.
3. Agent는 수행 가능 여부를 판단하고 `acknowledged`, `running`, `rejected` 중 하나로 actual state를 기록한다.
4. Agent는 실행 중 주기적으로 snapshot을 기록한다.
5. Agent는 테스트 결과와 최종 완료 상태를 명시적으로 기록한다.

이 방식은 최초 지시문, 전체 방향성, 테스트 요구사항, 취소/재시도 같은 중요한 상태에 우선 적용한다.

## 6. Hook 기반 lifecycle 보고

기본적인 진행 단계는 hook과 heartbeat로 정기 보고한다.

1. Agent는 heartbeat를 주기적으로 보낸다.
2. Agent는 현재 진행 단계와 최근 수행 작업을 lifecycle report로 보낸다.
3. Agent는 직전 지시 또는 최근 참조 지시를 함께 보낼 수 있다.
4. Agent는 완료한 체크박스와 산출물 참조를 보낸다.
5. 웹 계층은 이를 서버측 기록과 대시보드 표시용으로 저장한다.

## 7. 이벤트 수집

1. 수집 API가 이벤트 스키마와 인증을 검증한다.
2. 중복 이벤트인지 확인한다.
3. 이벤트 원본을 저장한다.
4. 최신 상태 스냅샷을 갱신한다.
5. 알림이나 비동기 후처리가 필요한 이벤트는 선택적으로 메시지 브로커에 발행한다.

## 8. 화면 표시와 알림 전달

1. 웹 계층이 정제된 최신 상태를 대시보드에 표시한다.
2. 사용자의 관심 프로젝트, 에이전트, 지침 조건에 맞는 상태만 보여준다.
3. 중요 이벤트는 페이지 내부 모달 알림으로 표시한다.
4. 사용자가 권한을 허용한 경우 브라우저 알림을 보낸다.
5. RabbitMQ를 사용하는 경우 알림 실패를 재시도하고 실패 이력을 남긴다.

## 7. 장애 처리

### 에이전트 오프라인

- heartbeat가 일정 시간 이상 없으면 `offline` 상태로 표시한다.
- 진행 중이던 지시는 `stale` 또는 `unknown` 상태로 표시한다.

### 이벤트 지연

- `occurred_at`과 `received_at` 차이를 기록한다.
- 지연이 임계치를 넘으면 관측성 지표와 알림을 발생시킨다.

### 중복 이벤트

- `event_id` 또는 `instruction_id + sequence`로 중복을 제거한다.

### 순서 뒤섞임

- 이벤트 발생 시각과 sequence를 함께 사용한다.
- 최신 상태 갱신 시 더 오래된 sequence가 현재 상태를 덮어쓰지 않도록 한다.

### 테스트 완료 미확인

- 구현 완료와 테스트 완료를 같은 상태로 취급하지 않는다.
- 에이전트가 테스트 결과를 명시적으로 보내지 않으면 `completed` 상태까지만 표시한다.
- 테스트 확인이 필요한 지침은 `test_pending` 또는 `verification_required`로 표시한다.

### Agent 미응답

- Agent가 desired state를 읽지 않으면 `unacknowledged`로 표시한다.
- Agent가 읽었으나 수행하지 않으면 `acknowledged`로 표시한다.
- 마지막 heartbeat가 오래되면 `offline`으로 표시한다.
- 마지막 snapshot이 오래되면 `stale`로 표시한다.

## 운영 프로세스

### 상태 코드 관리

- 공통 상태 코드는 중앙 문서로 관리한다.
- 새 상태 코드는 기존 대시보드와 구독 조건에 미치는 영향을 검토한 뒤 추가한다.
- `completed`, `tested`, `completed_and_tested`의 차이를 명확히 유지한다.
- `high` 신뢰도 상태와 `medium` 신뢰도 lifecycle 이벤트를 구분한다.

### 이벤트 스키마 변경

- 스키마 버전을 둔다.
- 하위 호환 필드를 유지한다.
- 구독자별 지원 버전을 추적한다.

### 보존 정책

- 최신 상태 스냅샷은 장기 보존한다.
- 상세 이벤트는 프로젝트 중요도에 따라 보존 기간을 다르게 둔다.
- 민감 데이터 포함 가능성이 있는 payload는 별도 마스킹 또는 암호화를 적용한다.
