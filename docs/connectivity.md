# 연결성 검토: Hook 기반과 MCP 기반

## 질문

MCP를 사용하면 에이전트의 세션과 상호 연결성을 보장할 수 있는가?

## 결론

MCP는 hook 기반 단방향 전송보다 높은 수준의 상호 연결성을 제공할 수 있다. 하지만 MCP만으로 에이전트의 내부 작업 세션, 장기 실행 지침, 테스트 완료 상태, 결과 전달까지 완전히 보장한다고 보기는 어렵다.

따라서 연결성은 다음 두 계층으로 나누어 정의한다.

- 프로토콜 연결성: MCP가 비교적 잘 다룰 수 있는 영역
- 지침 실행 신뢰성: 별도의 상태 저장, 이벤트 기록, 재시도, 검증 모델이 필요한 영역

또한 MCP를 사용하더라도 실제 작업 실행과 최종 제어권은 Agent에 있다. 웹 계층은 Agent에게 강제로 명령을 주입하거나 실행을 탈취하지 않고, Agent가 읽을 수 있는 상태와 지침을 제공하여 간접적으로 다음 행동을 유도한다.

## Hook 기반 연결성

Hook 기반 모델은 에이전트가 상태 변화를 단방향으로 전송하는 구조이다.

장점:

- 구현이 단순하다.
- 에이전트가 어떤 환경에 있든 HTTP 호출만 가능하면 붙일 수 있다.
- 기존 hook, skill, 실행 결과를 그대로 활용하기 쉽다.

한계:

- 웹 계층이 에이전트의 현재 세션 상태를 직접 알기 어렵다.
- 이벤트가 누락되면 중간 진행 상태를 복구하기 어렵다.
- 에이전트가 살아 있는지, 작업을 계속 수행 중인지 별도 heartbeat 없이는 판단하기 어렵다.
- 상호작용이 필요한 경우 별도 API를 추가해야 한다.

## MCP 기반 연결성

MCP 기반 모델은 에이전트 또는 에이전트 주변 어댑터를 MCP client/server 구조로 연결하는 방식이다.

기대할 수 있는 점:

- 초기화와 capability negotiation을 통해 상대가 어떤 기능을 제공하는지 확인할 수 있다.
- JSON-RPC 기반 요청/응답 구조를 사용할 수 있다.
- transport에 따라 양방향 메시지 교환이 가능하다.
- Streamable HTTP transport에서는 서버가 세션 ID를 부여하고, 클라이언트가 이후 요청에 해당 세션 ID를 포함하는 방식으로 세션 연속성을 표현할 수 있다.

하지만 MCP가 자동으로 보장하지 않는 것:

- 에이전트 내부의 장기 작업 세션 보존
- 지침 실행 단계의 영속 저장
- 누락 이벤트 자동 복구
- 테스트 완료 여부의 진실성
- 에이전트 프로세스 재시작 후 동일 작업 복구
- 여러 에이전트에 걸친 분산 작업의 정확한 완료 판정

## 제어권 원칙

이 시스템은 Agent를 강압적으로 제어하지 않는다.

사용하지 않는 방식:

- SSH 접속을 통한 원격 명령 실행
- 프로세스 강제 중단 또는 재시작
- 파일 시스템 직접 조작
- Agent 내부 큐나 메모리 상태 직접 변경

사용하는 방식:

- Agent가 주기적으로 MCP 또는 hook endpoint와 통신한다.
- Agent가 자신의 현재 상태를 보고한다.
- 웹 계층은 Agent가 읽을 수 있는 지침 상태를 저장한다.
- Agent는 다음 주기에 상태를 읽고 스스로 수행 여부를 판단한다.
- 웹 계층은 완료, 실패, 테스트 결과를 수신하고 검증 가능한 형태로 보관한다.

이 방식은 즉각적인 강제성은 낮지만, Agent의 독립성과 실행 환경을 보존한다. 개인용 또는 소수 사용자 대상의 신뢰 가능한 관찰 시스템에는 이 모델이 더 적합하다.

## MCP 상태 저장 방식

MCP를 도입할 경우, MCP 연결은 명령 실행 채널이라기보다 상태 조회와 간접 지시 전달 채널로 사용한다.

### Agent가 읽는 상태

- 할당된 지침
- 지침 원문 또는 요약
- 단계 목록
- 체크박스 목록
- 우선순위
- 취소 요청 여부
- 일시정지 요청 여부
- 사용자 입력 또는 확인 요청
- 테스트 요구사항

### Agent가 쓰는 상태

- 현재 실행 중인 지침
- 현재 단계
- 완료한 체크박스
- 진행 메시지
- 차단 사유
- 산출물 참조
- 테스트 실행 여부
- 테스트 결과
- 최종 완료 선언

### 간접 명령 모델

웹 계층이 Agent에게 명령을 직접 실행시키는 대신, Agent가 주기적으로 읽는 상태에 의도를 남긴다.

예:

```json
{
  "instruction_id": "inst-001",
  "desired_state": "run",
  "requested_actions": ["execute", "test", "report"],
  "cancel_requested": false,
  "pause_requested": false
}
```

Agent는 이 상태를 읽고 자신의 정책에 따라 수행한다. 수행 결과는 다시 상태로 기록한다.

이 모델에서는 명령 전달이 "즉시 실행"이 아니라 "다음 확인 주기에서 Agent가 수락하고 실행"하는 방식이다.

## 주기 통신

안정적인 운용을 위해 Agent는 MCP 또는 hook endpoint와 주기적으로 통신해야 한다.

권장 주기:

- heartbeat: 10-30초
- 실행 중 instruction snapshot: 10-60초
- 긴 작업 로그 요약: 1-5분
- 테스트 결과와 최종 완료 상태: 즉시 전송

상태 판정:

- 마지막 heartbeat가 임계치를 넘으면 `offline`
- 실행 중 snapshot이 오래 갱신되지 않으면 `stale`
- 완료 이벤트는 있으나 테스트 결과가 없으면 `test_pending`
- Agent가 지침을 읽었으나 수행하지 않으면 `acknowledged`
- Agent가 지침을 거부하면 `rejected`

## 신뢰도 모델

### 낮은 신뢰도 모델: Hook Only

에이전트가 hook으로 상태를 보내고, 웹 계층은 받은 정보만 저장한다.

적합한 경우:

- 개인용 또는 소수 사용자 대상 MVP
- 에이전트 수가 적음
- 실시간 제어보다 완료 확인이 중요함
- 일부 진행 누락을 허용할 수 있음

필수 보완:

- event_id
- instruction_id
- sequence
- occurred_at
- received_at
- heartbeat
- 최종 완료와 테스트 완료 분리

### 중간 신뢰도 모델: Hook + Heartbeat + Snapshot

Hook 기반은 유지하되, 에이전트가 주기적으로 현재 작업 스냅샷을 보낸다.

적합한 경우:

- 진행 상태 누락을 줄이고 싶음
- 에이전트 오프라인 감지가 필요함
- 작업 완료 판정의 신뢰도를 높이고 싶음

추가 요소:

- agent heartbeat
- instruction snapshot
- checklist snapshot
- test_result snapshot
- stale 상태 판정

### 높은 신뢰도 모델: MCP Adapter + Persistent State

에이전트 또는 에이전트 주변에 MCP adapter를 두고, 웹 계층이 MCP를 통해 기능과 세션을 확인한다. 단, 지침 실행 상태는 여전히 별도 저장소에 영속화한다.

적합한 경우:

- 에이전트와 상호작용해야 함
- 에이전트 기능 목록을 동적으로 알고 싶음
- 세션 단위 요청/응답과 상태 확인이 중요함
- hook 누락이나 단절 후 복구가 중요함

추가 요소:

- MCP lifecycle 관리
- MCP session_id 추적
- capability registry
- instruction state store
- reconnect 처리
- server-side snapshot API
- 테스트 결과 검증 이벤트
- Agent polling 또는 heartbeat 주기
- desired state와 actual state 분리

## 권장 방향

현재 프로젝트는 소수 외부 사용자 대상이고, 에이전트의 hook과 skill에 의존할 가능성이 높다. 따라서 초기에는 낮은 신뢰도 모델에서 시작하되, 설계는 중간 신뢰도 모델까지 바로 확장 가능하게 잡는 것이 적절하다.

즉, MVP는 다음을 권장한다.

- HTTP hook 수신
- event_id와 sequence 기반 멱등 처리
- 지침별 가변 단계와 체크박스 저장
- 완료와 테스트 완료 상태 분리
- agent heartbeat 추가
- 최신 snapshot 수신 API 추가

다만 최초 지시문, 전체 방향성, 정책성 상태처럼 신뢰도가 중요한 정보는 높은 신뢰도 모델을 적용한다. 일반 진행 보고와 heartbeat는 중간 신뢰도 모델을 사용한다.

## 혼합 신뢰도 모델

현재 설계는 높은 신뢰도 모델과 중간 신뢰도 모델을 혼용한다.

### 높은 신뢰도 영역

최초 지시문이나 전체 방향성을 나타내는 행위에 사용한다.

대상:

- 최초 지시문
- 지침 원문
- 전체 목표
- 작업 방향성
- 실행 정책
- 테스트 요구사항
- 중단, 취소, 재시도 같은 사용자 의도
- Agent가 반드시 인지해야 하는 상태

권장 방식:

- MCP 기반 상태 조회 또는 명시적 acknowledge
- desired state와 actual state 분리
- Agent의 수락 여부 기록
- 지침 버전 관리
- 누가 언제 지침을 변경했는지 기록

핵심 판정:

- Agent가 지침을 읽었는가
- Agent가 지침을 수락했는가
- 현재 실행 중인 지침 버전이 최신인가
- 테스트 요구사항을 인지했는가

### 중간 신뢰도 영역

기본적인 에이전트 진행 단계와 lifecycle 보고에 사용한다.

대상:

- 현재 진행 단계
- 완료한 체크박스
- 직전 수행 작업
- 직전 지시 또는 최근 참조 지시
- 진행 메시지
- 산출물 참조
- heartbeat
- 주기적 snapshot
- 단순 서버측 기록용 이벤트

권장 방식:

- HTTP hook
- 주기적 lifecycle report
- heartbeat
- snapshot
- event_id와 sequence 기반 멱등 처리

핵심 판정:

- Agent가 살아 있는가
- 최근 어떤 작업을 했는가
- 진행 단계가 갱신되고 있는가
- 지연 또는 멈춤 상태인가
- 서버 기록용으로 충분한 이력이 남았는가

## 혼합 모델의 장점

- 중요한 지침 전달은 신뢰도 높게 관리한다.
- 빈번한 진행 보고는 가볍게 처리한다.
- 모든 이벤트를 MCP로 처리하지 않아도 된다.
- 모든 상태를 hook-only로 처리할 때보다 지침 인지 신뢰도가 높다.
- SSH 같은 강제 제어 없이도 Agent와 웹 계층 사이의 상태 일관성을 높일 수 있다.

## 혼합 모델의 주의점

- 높은 신뢰도와 중간 신뢰도 이벤트의 경계를 명확히 해야 한다.
- 진행 보고가 누락되어도 최초 지침 자체가 흔들리면 안 된다.
- Agent가 어떤 지침 버전을 수행 중인지 항상 기록해야 한다.
- 완료 판정은 hook 보고만으로 확정하지 않고, 테스트 결과와 지침 버전을 함께 확인해야 한다.

MCP는 모든 상태 전송의 필수 기반이 아니라, 다음 요구에 사용한다.

- 에이전트 기능을 동적으로 탐색해야 한다.
- 웹 계층에서 에이전트에게 상태 확인을 요청해야 한다.
- 단순 hook보다 더 강한 상호작용이 필요하다.
- 에이전트 세션을 연결 단위로 추적해야 한다.
- Agent가 주기적으로 상태를 읽고 간접 지시를 수행하는 구조가 필요하다.

## 남은 확인 질문

1. 에이전트가 MCP server가 될 수 있나요, 아니면 별도 adapter가 필요할까요?
2. 웹 계층이 에이전트에게 상태 확인 요청을 보내야 하나요?
3. 에이전트가 장기 실행 중 재시작될 가능성이 있나요?
4. 테스트 완료 여부는 에이전트가 선언하면 충분한가요, 아니면 별도 검증자가 확인해야 하나요?
5. Agent의 heartbeat와 snapshot 주기는 어느 정도가 적절한가요?
6. `pause`, `cancel`, `retry` 같은 요청을 간접 지시로 포함할까요?
