# 구독 개념 정의

## 이 프로젝트에서의 구독

이 프로젝트에서 "구독"은 일반적인 개발에서 말하는 pub/sub과 다르게 정의한다.

일반적인 pub/sub은 발행자와 구독자가 메시지 브로커를 중심으로 느슨하게 연결되고, 여러 소비자가 토픽을 구독하는 구조를 의미한다. 하지만 이 시스템의 핵심은 에이전트를 제어하거나 에이전트와 양방향으로 종속되는 것이 아니다.

여기서 구독은 다음에 가깝다.

> 에이전트가 hook, skill, 실행 결과, 상태 이벤트를 단방향으로 보내고, 웹 계층이 이를 받아 정제한 뒤 사용자에게 상태와 알림으로 제공하는 구조

## 방향성

### 단방향 수신

- 기본 흐름은 `agent -> hook receiver -> web layer -> user display/notification`이다.
- 웹 계층은 에이전트의 실행을 직접 제어하지 않는다.
- 에이전트는 가능한 시점에 상태를 보고한다.
- 웹 계층은 보고받은 상태를 신뢰 가능한 형태로 정리하고 저장한다.

### 에이전트 의존성

상태 품질은 에이전트가 제공하는 hook, skill, 실행 지침, 체크리스트 정보에 의존한다.

따라서 시스템은 모든 에이전트에 동일한 진행률 계산을 강제하지 않는다. 대신 지침별로 제공되는 단계와 체크 항목을 그대로 수용하고, 공통 화면에서 비교 가능한 형태로 정제한다.

## 구독 대상

구독 대상은 메시지 브로커의 토픽만을 의미하지 않는다.

- 특정 프로젝트
- 특정 에이전트
- 특정 지침
- 특정 지침의 단계
- 특정 체크박스 항목
- 완료와 테스트 검증 상태
- 실패, 차단, 사용자 확인 필요 상태

## 수신 데이터

에이전트 hook에서 받을 수 있는 데이터는 다음을 우선한다.

- 현재 지침 ID 또는 지침 제목
- 지침 원문 또는 요약
- 지침에 포함된 단계 목록
- 현재 단계
- 완료된 단계
- 지침 내 체크박스 목록
- 체크박스별 완료 여부
- 테스트 수행 여부
- 테스트 결과
- 최종 완료 여부
- 오류 또는 차단 사유
- 관련 산출물 링크

## 가변 단계 모델

지침마다 작업 구조가 다르므로 고정된 단계 모델을 강제하지 않는다.

예:

```markdown
- [x] 요구사항 파악
- [x] 초안 작성
- [ ] 테스트 또는 검증
- [ ] 최종 보고
```

웹 계층은 이 정보를 받아 다음처럼 정제할 수 있다.

- 전체 체크 항목 수
- 완료 체크 항목 수
- 현재 진행 중인 항목
- 완료율 참고값
- 테스트 완료 여부
- 최종 완료 여부

완료율은 보조 지표이며, 가장 중요한 기준은 "지침이 완전히 완료되었고 테스트까지 끝났는가"이다.

## 알림과 구독의 관계

구독은 상태를 받아보는 개념이고, 알림은 받아본 상태 중 사용자에게 즉시 표현할 필요가 있는 것을 드러내는 방식이다.

초기 알림 방식:

- 브라우저 알림
- 페이지 내부 모달 알림

추후 알림 방식:

- 이메일
- 메신저
- Webhook

## 메시지 브로커의 역할

RabbitMQ 또는 MQTT는 에이전트와 웹 계층 사이의 필수 전제라기보다, 수신 이후 내부 분배나 알림 전달을 안정화하기 위한 선택지로 본다.

### RabbitMQ가 적합한 경우

- 작업 큐와 재시도가 중요하다.
- 알림 전달 실패를 다시 처리해야 한다.
- 상태 이벤트를 여러 내부 소비자가 나눠 처리한다.
- 라우팅 규칙이 비교적 명확하다.

### MQTT가 적합한 경우

- 에이전트가 가볍고 자주 상태를 보낸다.
- 온라인/오프라인과 연결 상태가 중요하다.
- 토픽 기반 상태 수신이 자연스럽다.
- IoT나 경량 런타임과 비슷한 환경이다.

### 초기 판단

초기 구현은 HTTP hook 수신을 기본으로 두고, 웹 계층 내부에서 RabbitMQ를 선택적으로 붙이는 방향이 가장 단순하다.

MQTT는 에이전트가 매우 많거나 연결 상태 자체를 중요한 상태로 다뤄야 할 때 검토한다.
